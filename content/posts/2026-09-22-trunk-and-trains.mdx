Friday afternoon, someone does the stale-PR sweep. There's one sitting there from three weeks ago, the same diff as a fix that's already in production, rotted into a conflict with a feature branch nobody remembers opening. They close it. Nothing goes red. Nobody gets paged. Everyone has a nice weekend.

The bug is now back on the next train.

Here's how it got there. Two weeks before the train leaves, something breaks in `release/2026.09`. You open a PR into the release branch, because that's what ships. Then you open a second PR with the same diff into `develop`, because that's where everyone actually works. The first one is reviewed, merged and on staging before lunch. The second one is the one that died on Friday.

Nobody broke a rule. The rule was the bug.

I'm talking about a few hundred engineers in one repo, plus whatever fleet of agents they're running, shipping on a two-month train, with a development branch that's supposed to be stable enough to demo from on a Tuesday afternoon. Git-flow can't give you that. It was never trying to.

## It was right in 2010. It shipped on a disc.

Subversion turned up in 2000 and made a branch a cheap copy. Merging stayed expensive and stayed stupid. Until [version 1.5 in 2008](https://subversion.apache.org/docs/release-notes/1.5.html), SVN kept no record of what had already been merged, so you tracked it by hand in commit messages like an accountant with a hangover and hoped you never applied the same change twice. Teams did the rational thing. They branched rarely, merged with dread, and did the work on trunk. Google ran its entire codebase on one Perforce server for over a decade on exactly that instinct.

Git landed in 2005 and made branches free. GitHub landed in 2008 and made the pull request the unit of work, which Chris Wanstrath [announced](https://github.blog/news-insights/the-library/oh-yeah-there-s-pull-requests-now/) that February, before the site was even public. A branch per feature now cost nothing. Every branch needed a ceremony to get home.

Vincent Driessen's [A successful Git branching model](https://nvie.com/posts/a-successful-git-branching-model/) gave the ceremony a name in January 2010. `master` for production, `develop` for what's coming, feature branches off develop, release branches off develop, hotfix branches off master, and every release and every hotfix merging twice. The diagram has five lanes and the colour scheme of a Tokyo metro map, and for about eight years, printing it out was how you announced that you had a process.

It was a good model. It was correct for the software Driessen was writing, which shipped in numbered versions to customers who might sit on 2.3 until 2015.

Ten years later he stuck a note on the top of his own post saying web apps aren't that class of software, they roll forward and not back, and those teams should go and use GitHub flow instead.

<Quote author="Vincent Driessen, 2020 note on the git-flow post">
Panaceas don't exist. Consider your own context.
</Quote>

The reference implementation was [archived in October 2025](https://github.com/nvie/gitflow/issues/6470). Atlassian files its own git-flow tutorial under [legacy](https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow). And a large slice of every company founded before 2018 is still running it, usually in the mutant form where the release branch stays open for most of the cycle and `develop` is green by coincidence.

## The second merge is the whole bug

Everything else is a symptom.

A twin PR isn't one change in two places. It's two originals. The same fix, reviewed twice, by different people, against different bases, sometimes weeks apart, and there's nothing in git that says they're related. They can produce different trees, and often do. CI tested each of them, and neither run tells you anything at all about the combination, because the release branch never merges back cleanly and `develop` has moved three hundred commits in the meantime. Fowler's [Branching Patterns](https://martinfowler.com/articles/branching-patterns.html) puts it politely: it's too easy to neglect copying a fix over to the mainline, and it gets harder the further the branches drift. GitLab has had a [request open since 2020](https://gitlab.com/gitlab-org/gitlab/-/issues/276698) to automate the double merge, complete with a workaround that involves a third branch and switching your protections off. When a workflow needs a bot to remember its own steps, the workflow is shit. Bin it.

Only one of the two merges wakes anybody up at 3am. Guess which one gets forgotten. Not malice, not sloppiness, just people doing the thing the process rewards, which is what people have always done.

Then it compounds. The release branch that was cut for a two-week stabilisation window stays open for the whole cycle, because QA signs off there and only there, so that's where fixes go first, and someone forward-ports them later. Or doesn't. Two months in, you have two products wearing the same name. Adam Ruka [wrote about the other redundancy in 2015](https://www.endoflineblog.com/gitflow-considered-harmful): if every commit on master is a merge from a release branch, master carries nothing the tags don't already carry. Three branches, one of which is real.

Now look at the projects that genuinely ship versioned software on a schedule, at volume, with people shouting at them. None of them do twin PRs. The [Linux stable trees](https://docs.kernel.org/process/stable-kernel-rules.html) won't take a fix unless it already exists in mainline, and it has to be small and obviously correct. [Chromium](https://chromium.googlesource.com/chromium/src.git/+/main/docs/process/merge_request.md) is main-first: you fix on main, then a release manager reviews your request to merge it into a release branch within two business days, against criteria that tighten as you get closer to stable. [Kubernetes](https://github.com/kubernetes/community/blob/main/contributors/devel/sig-release/cherry-picks.md) fixes on master and opens one cherry-pick PR per supported branch, approved by the release team.

Same rule three times. One canonical change on the trunk, and a backport that's a mechanical copy with provenance rather than a second piece of work with its own opinions. That's your situation. Copy their homework.

## One trunk, trains every two months

```
main      ●──●──●──●──●──●──●──●──●──●──▶  always green
             │                    │
             └ release/2026.09 ●──●──▶ v2026.09.0 (prod)
               cherry-picks only  └ release/2026.11 ●──▶
feature/x ●──●──┐  two days, rebased on main, merge queue
agent/y   ●──┘
```

One long-lived branch. It's `main`. This is [scaled trunk-based development](https://trunkbaseddevelopment.com/branch-for-release/) with a train timetable nailed to it, and I invented none of it. It's the stable development branch you wanted, with one change you'll hate for about six weeks: it's held to release standard, not to "mostly works." Full pre-merge suite on every commit. Every merge redeploys it to an integration environment that product, sales and QA can open whenever they like. When someone asks to see where the new checkout got to, the answer is a URL, not a branch name and an apology.

Fowler calls this a [release-ready mainline](https://martinfowler.com/articles/branching-patterns.html), and the part everyone skips is that it doesn't mean you release every commit. It means you could. The real test isn't what CI says. It's whether you'd let a salesperson click around it during a customer call without hovering behind them.

Feature branches come off `main` and go back within days. Rebase your private branch onto `main` every morning, so conflicts arrive one at a time while they're still small, and never force-push a branch someone else has checked out, because that's how friendships end. You don't merge to `main` yourself. The merge queue does it, on top of whatever landed while you were arguing in review, so the thing that gets tested is the thing that ships.

Anything that takes longer than a train to build goes behind a [flag](https://martinfowler.com/articles/feature-toggles.html), or gets split into a stack of small PRs, or gets done as a [branch by abstraction](https://martinfowler.com/bliki/BranchByAbstraction.html). Schema changes go through [expand and contract](https://martinfowler.com/bliki/ParallelChange.html). The six-week feature branch that rebases weekly and lands as one 4,000-line PR is the exact thing this model exists to kill, because that PR is the one nobody reviews and the one most likely to be wrong. I've been handed a 200,000-line one. [My laptop hasn't forgiven me.](/blog/red-teaming-the-agent)

Release branches get cut from `main` on a fixed date, two weeks before the train, and named for the train: `release/2026.11`. From that moment it accepts cherry-picks of commits already on `main` and nothing else. Label the original PR, a bot opens the cherry-pick with `-x` so the commit records where it came from, and the release manager approves it against one question. Does this need to ride this train, or can it wait eight weeks? The bar goes up every week. Ship, tag, the branch goes quiet, it takes hotfix cherry-picks until the next train ships, and then it's dead. Two release branches alive at any time. Never three. If you have three, something has gone wrong upstream of your branching model and no diagram is going to save you.

The hotfix path is the same path, because there's no other one. Production is on fire, you fix it on `main`, and that's the only PR anyone reviews. The bot backports to the live release branch, the release manager approves, it deploys. The single exception is a fix that genuinely can't apply to `main` because the code has moved underneath it. Fine. Fix on the release branch, open the forward-port issue the same hour, and count it. Every one of those is a measurement of how far `main` and the release branch have drifted, and if that number isn't close to zero then you don't have a process, you have two codebases and a scheduling problem.

Environments follow the branches. A preview environment per PR, created on open, destroyed on merge. `main` deploys continuously to integration. The release branch deploys to staging and then production. No long-lived staging server fed by hand, ever, because a staging server that people push to is a branch with worse tooling and no history.

If you have a `master` that only ever receives merges from release branches, kill it. The tags already do that job. If your stable branch is called `develop` and there's nothing above it, keep the name, nobody cares. There has to be exactly one of it.

Two months between trains is fine. Chrome ran six weeks for a decade, went to four in 2021, and [moved to two weeks](https://developer.chrome.com/blog/chrome-two-week-release) this month, with the team [citing](https://developer.chrome.com/blog/chrome-two-week-start) the volume of patches coming out of automated AI discovery tools. Firefox started its own [two-week experiment](https://groups.google.com/a/mozilla.org/g/dev-platform/c/qlaQ1YSlOP8) on the first of September. Both are drifting shorter, and both run on the rule that matters more than the interval: the train leaves on time, and a feature that's not ready rides the next one. The interval is a business decision. The stabilisation window is not. If it takes you six weeks to get a release branch shippable, that's not a release problem. That's `main` telling you it was never release-ready when you cut it, and that you've been lying to yourself about what green means.

## Now run it with a few thousand PRs a day

None of the above is new. Big shops have run it for years. What changed is the load.

By April 2026 Sundar Pichai was [saying](https://www.semafor.com/article/04/24/2026/google-ceo-says-75-of-companys-new-code-is-ai-generated) three quarters of Google's new code is AI-generated and then approved by an engineer. Anthropic's [own retrospective](https://www.anthropic.com/institute/recursive-self-improvement) puts Claude's share of merged code at 80%, at eight times the lines merged per engineer per day compared with 2024. Uber [reports](https://www.uber.com/us/en/blog/efficient-software-factory/) over 70% of PRs attributed to agents. Across GitHub, merged PRs went from about 25 million a month in early 2023 to [about 90 million a month](https://github.blog/open-source/maintainers/how-pull-request-limits-are-cutting-down-the-noise/) by mid-2026. Three hundred engineers merging twice a day is six hundred PRs. Multiply by what those numbers imply and your trunk is eating a few thousand a day.

The pull request was invented so one human could explain a change to another human. Point a few thousand agents at it and the whole thing comes apart at the seams. LinearB's [benchmark](https://linearb.io/blog/8-million-prs-engineering-productivity) of 8 million PRs found AI-authored ones wait over sixteen hours for a first review against about three hours for human ones, and merge at 33% instead of 85%. A [study](https://arxiv.org/abs/2605.02273) of 33,000 agent PRs found 61% never got a human review at all. Run several agents on the same repo at once and [42% of PR pairs](https://arxiv.org/abs/2607.04697) conflict. Anthropic's CI job count [grew 25 times](https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic) in six months while headcount barely moved, and their test-selection service fell over three separate times before they rebuilt it.

So you add machinery. You don't add branches. Everybody's first instinct under load is to add a branch, because a branch feels like control. It isn't. It's a place to hide work until it becomes somebody else's problem.

Start with the merge queue, because at that volume nobody gets to merge to `main` by hand. Uber built [SubmitQueue](https://blog.acolyer.org/2019/04/18/keeping-master-green-at-scale/) after measuring that their iOS mainline was green 52% of the time, which is a coin flip you're paying a few hundred engineers to lose. The queue takes PRs in order, builds them speculatively stacked on each other, lands a batch only if the batch passes, and on failure bisects and ejects whoever broke it. Shopify ran [batches of eight](https://shopify.engineering/successfully-merging-work-1000-developers) at 400 commits a day with direct merges switched off at branch protection. GitHub's own engineers push [2,500 PRs a month](https://github.blog/engineering/how-github-uses-merge-queue-to-ship-hundreds-of-changes-every-day/) through theirs. The built-in queue is fine until you're doing many hundreds a day, at which point [the single queue and the missing bisection](https://trunk.io/blog/outgrowing-github-merge-queue) start to hurt and you go and look at Trunk, Aviator or Graphite.

Then stop running the full suite on every PR. At a few thousand a day that turns your CI bill into a number somebody in finance screenshots and forwards to your CEO, and the programme dies in a budget meeting you weren't invited to. Google's TAP runs presubmit on [over 50,000 changes a day](https://abseil.io/resources/swe-book/html/ch23.html) by testing only what a change can reach through the dependency graph. Bazel, Nx and Turborepo give you the same graph at human scale. Flake quarantine sits right next to it, with an owner, because a queue that ejects your PR for somebody else's flaky test is a queue people learn to route around inside a fortnight.

CODEOWNERS on every directory, so a PR that touches billing pulls in the billing owner as a required reviewer and everything else goes to whoever's free. A release manager on rotation with real authority to refuse a cherry-pick. A merge captain for the week who watches the queue and the flake board. At 300 people these stop being "ask someone senior" and become names on a schedule, and if they aren't on a schedule they aren't real.

Policy before review. The PR carries the metadata that decides who looks at it: lines changed, paths touched, tests removed, migration touched, auth module touched. Intercom [says](https://www.intercom.com/blog/ai-is-approving-our-pull-requests-heres-how-we-made-it-safe/) 93% of its PRs are agent-driven, 19% merge with no human involved at all, and the AI-authored backend changes get reverted less often than the human ones, which should annoy you slightly. Ona [auto-approves](https://ona.com/stories/auto-approving-low-risk-prs) anything under a thousand lines that doesn't touch migrations, infrastructure, auth or protobufs, and keeps a human on the merge button so the auditors have someone to look at. You don't have to like those thresholds to see the shape of it. Humans review by exception, and the exception list lives in a file, not in a culture.

Agent branches are ordinary branches with a prefix and a leash. One task, one branch, `agent/` or `copilot/` in the name, opened as a draft PR, CI held until a human approves the run, deleted on merge. The agent gets no merge rights. It gets the same queue as everybody else and a size cap that will irritate it. Google's guidance is that [around 100 lines](https://google.github.io/eng-practices/review/developer/small-cls.html) is a reasonable change and 1,000 is too large, and one recent [measurement](https://brodzinski.com/2026/07/3x-pull-request-size-ai.html) of an AI-heavy project watched the median PR triple from 66 lines to 210. Stacked PRs are how an agent that did real work gets it reviewed, because a chain of five dependent changes squashed into one diff is how you end up with the PR that melts a MacBook. Meta open-sourced [Sapling](https://engineering.fb.com/2022/11/15/open-source/sapling-source-control-scalable/) for this back in 2022. GitHub finally shipped [native stacks](https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/) in public preview this July, with the queue keeping a stack together.

Even the commit is up for renegotiation now. [Jujutsu](https://github.com/jj-vcs/jj), which Martin von Zweigbergk started at Google and [left this month](https://ersc.io/blog/martin-joins-ersc) to build a hosting company around, treats the working copy as a commit and keeps conflicts in the graph instead of stopping you dead. Zed's [DeltaDB](https://zed.dev/blog/introducing-deltadb) ties every edit to the conversation that produced it. Neither one changes the model above. Both make it much cheaper to keep a branch rebased, which is most of what the model asks of you.

## Nobody knows why the code exists

For twenty years, the answer to "why does this exist" was the commit message, maybe the PR description, and otherwise a person you could walk over to. When 80% of the code comes out of an agent in a session that's closed and gone, that person doesn't know either. The diff was never the knowledge. The difference now is that nobody has it.

That's the hole the new forges are digging into, and the one I'd watch is [Entire](https://entire.io/). Thomas Dohmke, who ran GitHub until 2025, [announced it](https://entire.io/blog/hello-entire-world) in February 2026 on a $60 million seed. The first product is Checkpoints, an [open-source CLI](https://github.com/entireio/cli) that hooks git and stores every agent session, the prompt, the transcript, the tool calls, the files touched, as refs inside the repository, next to the commit and never on your working branch. An append-only log of the reasoning, portable across Claude Code, Codex, Copilot, Cursor and whatever ships next quarter. Dohmke's pitch is that the diff is half the record. I made [the same argument in May](/blog/remedies-for-the-slop), and I'd add that capturing this now is a great deal cheaper than reconstructing it during an incident in 2028.

Cursor's [Origin](https://www.infoq.com/news/2026/08/cursor-origin-alternative-github/) went into beta in August, on the same day GitHub was down for the best part of eight hours, which is timing you can't buy. It's the other shape of the bet: a full forge with stacked PRs and an agent-aware merge queue, syncing both ways with GitHub so GitHub stays the system of record. They'd bought Graphite eight months earlier, so the queue and the stacks arrived in the box. GitLab's [Orbit](https://ir.gitlab.com/news/news-details/2026/GitLab-Announces-New-Capabilities-to-Give-Enterprises-Speed-and-Control-at-Agentic-Scale/default.aspx) builds a context graph over code, issues, pipelines and production signals so an agent can ask the platform instead of re-reading your repo from scratch every morning. Scott Chacon's [GitButler](https://blog.gitbutler.com/series-a) just raised a Series A on his line that generating change was never the hard problem, and that organising, reviewing and integrating it is.

GitHub's answer so far is that you write the knowledge down by hand and feed it to the agent. AGENTS.md, organisation-wide instruction files, [Copilot Memory](https://github.blog/changelog/2026-01-15-agentic-memory-for-github-copilot-is-in-public-preview/) that expires after 28 days, Copilot Spaces, and an [Agent HQ](https://github.blog/news-insights/company-news/welcome-home-agents/) dashboard where agents from five vendors report for duty. It works. It's also the wiki, and the wiki is always three years stale and maintained by someone who left in 2021.

Notice what none of them capture. Ownership and architecture. Those still live in CODEOWNERS and in catalogues derived from the code itself, the way [encore.dev](https://encore.dev/docs/platform/observability/encore-flow) redraws its service graph from the application model on every deploy. What the new forges store is the agent's reasoning. Who is accountable when it turns out to be wrong is still a human problem, and it's the bigger one.

So: don't switch forges this year. Do start writing agent sessions into the repo, because the format is a git ref and a git ref travels. And read every one of these launches as a report on what your own process can't answer. If the market is selling "why did this change happen" as a feature, it's because your repo can't tell you.

## Where to start on Monday

Measure the damage before you propose anything, because the senior person who's about to block you needs a number. Run `git log --oneline release/current..develop` and then the reverse. Count the commits that exist on one side only. Go and find the fixes that were opened as twin PRs and check how many of the second halves actually merged. Write down how long each of the last three release branches stayed open. That's your business case, and it cost you an afternoon.

Then make the trunk release-ready, which is the only genuinely hard step. Required CI on every PR, branch protection, no direct pushes, a merge queue, which on GitHub is a checkbox. Deploy the trunk to an integration environment on every merge. If you can't deploy the trunk today, that's the entire project until you can, and everything below this paragraph is decoration.

After that it's mostly deletion. Collapse to one long-lived branch and retire `master` if it only ever receives merges from release branches. Ban twin PRs outright: the only reviewed PR is the one to `main`, a label fires a bot that opens the cherry-pick with `-x`, and the release manager approves against the train's criteria instead of re-reviewing code that was already reviewed an hour ago. Kubernetes and Chromium both publish their criteria, so steal one and change the words.

Then shorten the stabilisation window to two weeks and hold the date. Anything longer than a train goes behind a flag, one flag per seam, removed the day it hits 100%. Set size and path rules and enforce them in the repo rather than in review culture, because review culture is the thing you have instead of rules. Make every environment except integration, staging and production ephemeral, one per PR, created on open and destroyed on merge, which also kills the last honest argument for a hand-fed staging branch. Put names against the release manager, merge captain and directory owner roles, and write the rotation down where the on-call rotation lives.

And change what you measure, because the old numbers have turned into noise. Revert rate per train. Days the release branch stayed open. Forward-ports per train. Time from open to merge. The share of merged code somebody on the team can actually explain out loud. PR count goes up on its own now, and celebrating it is like celebrating rain.

The last holdout is always the same guy, and he'll tell you the double merge has never actually bitten him. That's bollocks, and it takes ten minutes to prove. Run the query from the first paragraph. Put the list of fixes that only exist on one side up on the screen. It bit him in March. He just wasn't the one who had to fix it.
